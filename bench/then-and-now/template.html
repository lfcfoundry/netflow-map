Netflow Map: first version vs now

Lays out the same maps with the very first Netflow Map (2026.10.14.2136, then called Net Flow Map) and with the version in this page (__VERSION__, with every update since), taking turns, and tells you in plain words what changed. Nothing leaves this page.

Live view: each picture appears here as it is produced, one at a timePage: waiting to start

One picture at a time: the finished layout of the run that just ended, first version or now in turn, drifting slowly so the drawing speed shows as FPS (frames per second, higher is better). It is drawn by the renderer of that version of the app (first version: its own renderer; now: the renderer in the full app today, with the same choice of WebGL 2 or the plain canvas that the app makes on this machine), so the FPS is the app's drawing speed. Drawing is paused while a layout is being timed, so it does not disturb the layout numbers.

The verdict

    Layout time, same map, one after the other

    "Typical" is the middle of the runs, "best" the fastest. Lower is better in every time column. "Times faster" is typical first version divided by typical now (higher is better). A run that passed the time limit was stopped and counts as the limit, so those rows say "at least".

    Drawing speed of the finished picture

    FPS while the finished layout is drawn and slowly panned in this browser (higher is better). Taken once per map, in the first turn, one picture at a time, drawn by each version's own renderer.

    Idle memory of the layout links (what the compressor does)

    The first version keeps every link of a finished layout as a plain object. Now, once a big map has been left alone for 4 seconds, the links are packed by memory-compression 2.0.3 and the objects are let go. "As objects" is an estimate (a rule of thumb, usually within a third); "packed" is the real size of the packed bytes. Lower is better in every size and time column. "Exact" says every link came back with the same values. These maps are made up and very regular, so they pack far better than real data usually does; real data will be less dramatic.
