## Design rules
- Speed must not cost looks. Keep the three drawing backends visually identical (parity check in `test/browser.test.js`).
- Pick a drawing backend by a real startup test, never by `'gpu' in navigator`.
- A diagnostic page is one button and a plain-words verdict.
- Keep checks cheap: run the Node tests while working (`importers`, `archive`, `columns`, `sim`, `gif`; `fuzz.test.js 20` is a 20-second spot check), the browser test and the 70-second-per-seed fuzz run once when a design is settled.
- Anything that reads a user's file (zip, xlsx, XML, GML, DOT, CSV, JSON) must have a limit counted on what is really read, a plain-words message when it refuses, and a case in `test/archive.test.js` or `test/fuzz.test.js`. Writes past the end of a typed array are silently ignored in JavaScript: guard them.
- Never edit a file in place that the user attached or dropped in; the app works on copies.
- Imported text is untrusted: no `innerHTML` without `esc()`, CSV export neutralizes leading `= + - @`.

## Map of the code
Engine (`src/engine.js`): `prepare` (flat arrays) → `importance` (choke points by dominators, traffic in log space) → `flowExact` / `flowSim` → `mapGraph` → a layout (`layered`, `arcLayout`, `matrixLayout`, `shapeLayout`, `networkLayout`) → `build`. `compare` scores every view.
Page: `importers` → graph → `engine-client` (worker) → layout → `scene` → `render` backend.
Graphics card (WebGPU compute): `src/gpustress.js` (`probe` = real start-up test, `layout`, sanity check); `engine-client` asks the worker for the big piece (`gpuPiece` job), runs the card, hands the picture back (`stressTuning.external` hook) so the engine's own clean-up runs on it; any failure falls back to the processor. `src/tune.js` + `src/app/62-tune.js` are the tuning test (first-start question, Advanced tab). Never ask the card for anything without the probe having passed. `test/card.test.js` and `test/tune.test.js` use pretend cards.
River (Sankey): `src/sankey.js` (`NFMSankey.layout` / `apply` / `options` / `measure`) is now the River view in the app: the engine calls it when the page passes `sk` (`build(..., {view:'river', sk})`; without `sk` the old layered River stays, which the lab page uses as "before"), the scene draws it (`sankeyBands`/`sankeyNode` in `src/scene.js`; gradients through `ribbon.color2`), and `src/app/33-sankey.js` holds the hand edits (`S.V.sk`: colors, labels, order, bar places; saved with the view and in shared view text via `cleanSk`), their undo, the Look panel section and the click menus. Items are keyed by data id (`nodeId`), never by the engine's `n0`, so remembered order and places survive rebuilds. Lab: `bench/sankey/` + `tools/build-sankey-lab.mjs` -> `bench/net-flow-map-river.html` (before/after page), `test/sankey.test.js`, research in `docs/SANKEY.md`. Tester: `TESTER_ONLY=3d node bench/tester/run-local.js chromium` runs just the 3D step; `TESTER_ONLY=where` runs "Where the drawing time goes (WebGPU)" (`NFMProbe.frameTiming` / `explainTiming`: times each phase of a picture several ways, WebGPU against WebGL 2). Turning a big 3D map: `networkScene` keeps what each item and link looks like between pictures (`o.plan`), and `tessellate` in `src/render.js` writes plain straight links (every link on a big network) straight into one shared buffer, so a 3,000-item picture costs a few milliseconds there instead of fifteen; `test/force3d.test.js` checks both give the same picture. WebGPU keeps its buffers between pictures (`legacyBuffers` is the old make-new-ones way, for the diagnostic) and loops call `pace()` instead of waiting for the card after every picture; `test/probe.test.js` covers both with a pretend device. Card-side turning (3D network of 1,500+ plain straight links, no icons/arrows/bends): `makeRig`/`attachTurn` in `src/scene.js` give the scene `S.turnTo(cam,kmax)` which only works out camera numbers, the back-to-front order (radix sort) and the few visible names per angle; `drawRig` in `src/render.js` (WebGL 2 textures + WebGPU storage buffers, same fragment code as the normal drawing) does the projection, fading and link trimming on the card. `scheduleScene` in `src/app/30-map.js` uses it while turning (`S.turn.on`) and `settleTurn()` rebuilds the full identical scene 250 ms after the last angle (picking, exports, Canvas2D). Item records (`rec.x/y/w/h/o`) are refreshed lazily by `S.syncRecs()` (flag `S.recStale`; called by `pick`/`inRect`/`inLasso` and `sceneNodeFor`: anything new that reads item places after a turn must call it), the pick grid by `S.gridStale`; the name labels are kept and moved from angle to angle (`lpool`), so a turn allocates almost nothing. Tests: card-side block in `test/force3d.test.js`, card vs full picture in `test/browser.test.js`; the tester times it as "math on the card". Links are 4-point triangle strips whose texels carry both end places (`rig.edgeG`), so the card does no second look-up. WebGL 2 sends the paint order through a ring of 3 attribute buffers by default; `rigDebug.orderVia = 'texture'` (tester way `tex`) sends it through an RGBA32UI texture instead, same picture (checked in `test/browser.test.js`); keep the default until laptop results say which is faster. WebGPU has three ways too (`rigDebug.orderVia` / `out.orderVia`: `write` = one buffer + writeBuffer (default: on the laptop with no leaks it ran 60/60/56 at 100,000 items, p95 19 ms), `map` = five MAP_WRITE staging buffers written directly and copied on the card (45/53/55, worse) and `ring` = three buffers (46/38/37, worst); earlier runs that favored `map` were run while the destroy leak below was eating memory, so do not trust comparisons made on builds before v2026.10.16.2019); tester ways `ring`/`map` compare them to the default, and `explainSplit` blames the paint order when pauses vanish without the re-send (the "nothing drawn" row alone is not trusted: the refresh runs slower with an unchanged canvas). `NFMProbe.turnSplit` / `explainSplit` (tester section "Turning the largest map: where the time goes") splits that turning into angle math, card time (links, items, names, half size, via the renderer's `rigDebug` switches) and the spread of picture times, and says in words which one holds it below 60.
- WebGPU `destroy()` must destroy every buffer one by one (rings are arrays) and always call `device.destroy()` last; an early v2357 version threw on the ring array and skipped the device, leaking memory until 100,000-item tests ran out of memory (checked in `test/browser.test.js`: leaving WebGPU destroys the device).
- Tester page order: the step being tested is the top card while it runs (`addSection` inserts at the top); when it finishes `main.fin` puts the "All done" buttons first (CSS `order`), then the turning 3D map (`#show`), then every step back in test order.
- Tester live view: while a section runs, `s.rows.push` redraws its table at once (rows appear one by one), `setStatus` is mirrored into the open card's "Working… now testing" line, `s.scatter(X, k, caption, stride)` draws a flat picture of the positions just worked out, and `s.live()` makes a box that `NFMProbe.turning` / `turnSplit` / `frameTiming` draw into (option `live`; `mkHost` in probe.js scales the real 900x600 picture into it, otherwise the host stays almost invisible in the page corner). The box is removed when the section finishes.
- Tester sizes everywhere (not quick mode): 5,000 / 25,000 / 50,000 / 100,000 in the layout ladder (moderate to 100,000, complex to 25,000), the parallel-pairs variants (5,000 and 25,000, plus old steps at 50,000 and 100,000), the drawing-time step and the 3D section. The smooth sweep (`sgd`) is skipped above 30,000 items (minutes). The correctness check stays at 1,200 items because its reference runs on the processor. The extras-only steps are unchanged.
- Tester 3D section sizes are 5,000 / 25,000 / 50,000 / 100,000 (3D force is built up to 30,000, spheres and stacks above). The turning picture at the end (`addPreview`) uses the card path like the app (rig scene, `rigPrepare`, `turnTo` only when the angle changes or zoom passes kmax, one `resize`, draws only when something moved, eased wheel zoom) and has a button per size; it used to rebuild the whole scene and resize the canvas on every wheel tick, which made zooming out (every item on screen) awful. Rows named "zooming in and out on the card" come from `NFMProbe.turning({zoomSweep:true})` (a quarter size to four times). `?preview=webgl2` forces the preview backend for testing. The preview also has a live FPS pill and records frame gaps while the person drags, scrolls or lets it turn; the "Your hands-on test" table is added to the results every time Download or Copy is pressed.
- Zooming and panning a big 3D map (`requestDraw` in `30-map.js`) ride the card like turning does: the first moved view enters card mode (`turnTo`), there is no automatic rebuild after movement stops any more (`armSettle()` is a no-op): rebuilding the full scene froze the next drag (0.2 s at 25,000 items, 1 to 2 s at 100,000, plus a fresh upload to the card). Whatever needs the full scene calls `settleTurn()` (save, print) or reads through `liveScene()` (brings the lazy item records up to date); any content change rebuilds the scene anyway. `browser.test.js` checks zooming after a settle goes back onto the card. Note the test reads the scene state right after `settleTurn()` (before any awaited draw): a draw at a different view legitimately flips the settled scene back onto the card.
