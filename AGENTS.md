## What this is
The product is called **Netflow Map** (one word; the owner renamed it on 2026-10-17, it was "Net Flow Map"). Its home is `https://github.com/lfcfoundry/netflow-map` (private). Old rows in the full changelog and saved results in `bench/results/` keep the old name on purpose.

`index.html` is built from `src/` by `node tools/build.mjs`. It must stay ONE self-contained file that works offline. The engine source is embedded as text so the same code runs in a Web Worker (from a Blob) and on the page.

## Design rules
- Speed must not cost looks. Keep the three drawing backends visually identical (parity check in `test/browser.test.js`).
- Pick a drawing backend by a real startup test, never by `'gpu' in navigator`.
- A diagnostic page is one button and a plain-words verdict.
- Fast way to run everything (2026-10-17): `node test/all.js` runs every Node test four at a time in about 17 s (`--full` gives the fuzz test its 90 s and every size at full). `NFM_TIMES=1 node test/browser.test.js firefox|chromium|webkit` prints the seconds each check took and a final total. The browser test opens the page with `?tunesizes=1500` and sets `window.NFM_CHECK_MS` so the device check uses small samples (`NFM_FULLCHECK=1` restores the full ones, `NFM_SLOW=1` the old fixed pauses). Waits in tests: use `settle(ms)` (waits for real animation frames and `NFM.pending() === 0`) for the screen catching up; keep `sleep(ms)` only for real time (easing, playback, a typing delay that the page does not count).
- Tester rules learned from the owner's laptop (2026-10-17): never label a skipped measurement "in the background" unless `document.hidden` said so (slow is not hidden: give slow ways more time and report what they did); a section's verdict must cover every size, not the last one; close the compute GPU device before the drawing tests; the Firefox/Radeon 780M laptop showed random 1.5 to 1.9 s freezes in WebGPU (and, less often, in WebGL 2), so the owner then decided (2026-10-17) that the app does not draw with WebGPU at all (`NFMRender.setWebGPUDrawing`, off by default; the browser test switches it on to keep testing that code). WebGPU compute for the card arrangement is unaffected.
- Memory (2026-10-17, measured in Node with `--expose-gc`): at 100,000 items one full 3D picture keeps about 150 MB alive (about 300,000 link objects, 100,000 item, label and dot objects) and the layout alone about 320 MB; typed-array number data is only a few MB. So squeezing numbers (16-bit positions) or reusing buffers gains almost nothing; the gains are fewer objects (not made at all while the map lives on the card, not done yet: picking, highlighting, exports and `rigStyle` still read `S.curves`) and not holding two pictures at once (`releaseOldScene` in `30-map.js`, from 20,000 items; tests set `window.NFM_RELEASE_MIN`).
- Tiers (2026-10-17): while working run `node test/all.js --changed` (or `--only=REGEX`); when a change is done add the browser test in ONE browser; the full Node run, then each approved browser one at a time, only when a design is final. Every browser run prints the browser's real version on line 1 and fails if it passes fewer checks than `test/baseline.json` (bless with `NFM_BLESS=1` after a reviewed change). Failures that pass on a rerun go in `docs/FLAKES.md` (name the check and browser first, then rerun once). Send the owner the tester only when it has something new for him to test.
- Bug-hunt regression files (2026-10-17): `test/import-fixes.test.js` (imports), `test/engine-fixes.test.js` (engine, scene, simulator, Sankey; includes `edgeFacets`, the engine reads a LIST of link filters and an edge must pass all of them; `edgeFacet` stays for the old single option), the new cases in `test/browser.test.js` (page). Browser baselines after that batch: chromium 132, firefox 112, webkit 121.
- Bug hunt (only when a design is final; judgment calls go to the owner, clear bugs get a failing test first, then the fix, then a regression case): (1) three read-only code reviews that only write findings; (2) fuzz at a chosen budget (`node test/all.js --full`, `test/fuzz.browser.js`) and shrink every failure; (3) oracles for anything that calculates (`oracle.test.mjs`) and the awkward-input list (`awkward.test.js`: add a new odd input there when a bug is found); (4) mutants: break each new check once and see it fail. Label findings Confirmed (re-read the line or ran a one-liner), Reported (read by an agent, not rechecked) or Unverified.
- Keep checks cheap: run the Node tests while working (`importers`, `archive`, `columns`, `sim`, `gif`; `fuzz.test.js 20` is a 20-second spot check), the browser test and the 70-second-per-seed fuzz run once when a design is settled.
- Anything that reads a user's file (zip, xlsx, XML, GML, DOT, CSV, JSON) must have a limit counted on what is really read, a plain-words message when it refuses, and a case in `test/archive.test.js` or `test/fuzz.test.js`. Writes past the end of a typed array are silently ignored in JavaScript: guard them.
- Never edit a file in place that the user attached or dropped in; the app works on copies.
- Imported text is untrusted: no `innerHTML` without `esc()`, CSV export neutralizes leading `= + - @`.
- **WebAssembly Force (2026-10-17):** `wasm/force.c` is a line-for-line port of `forceSim`'s rounds; `src/engine.js` carries its bytes between `WASM:BEGIN` and `WASM:END`. If you change the JavaScript `forceSimJs`, change `force.c` the same way, then `sh wasm/build.sh && python3 wasm/embed.py && node tools/build.mjs`; `test/force-wasm.test.js` must show a largest position difference of 0. The JavaScript stays the fallback. See `wasm/README.md`.
- **WebAssembly Distances layout (2026-10-17):** `wasm/stress.c` is a port of `stressComponent`'s pair building, shuffle and sweeps and of `separate`'s grid passes (2D); `src/engine.js` carries its bytes between `WASM:stress:BEGIN` and `WASM:stress:END` (the Force module uses `WASM:force:`). Pairs are two item numbers plus a Uint16 hop code (hops 1 to 511, +512 for pivot pairs, two 1,024-entry float32 tables): if you change `stressJs`, `sgdSweepCode`, `hopTables` or `separate`, change `stress.c` the same way, then `sh wasm/build.sh && python3 wasm/embed.py && node tools/build.mjs`; `test/stress-wasm.test.js` must show a largest position difference of 0. The JavaScript stays the fallback. See `wasm/README.md`.

## Map of the code
Engine (`src/engine.js`): `prepare` (flat arrays) → `importance` (choke points by dominators, traffic in log space) → `flowExact` / `flowSim` → `mapGraph` → a layout (`layered`, `arcLayout`, `matrixLayout`, `shapeLayout`, `networkLayout`) → `build`. `compare` scores every view.
Page: `importers` → graph → `engine-client` (worker) → layout → `scene` → `render` backend.
Graphics card (WebGPU compute): `src/gpustress.js` (`probe` = real start-up test, `layout`, sanity check); `engine-client` asks the worker for the big piece (`gpuPiece` job), runs the card, hands the picture back (`stressTuning.external` hook) so the engine's own clean-up runs on it; any failure falls back to the processor. `src/tune.js` + `src/app/62-tune.js` are the tuning test (first-start question, Advanced tab). Never ask the card for anything without the probe having passed. `test/card.test.js` and `test/tune.test.js` use pretend cards.
Sankey: `vendor/netflow-sankey.js` (exact copy of JS-modules netflow-sankey 2.2.1; `NetflowSankey.layout` / `apply` / `options`; the yardstick `measure` lives in `test/sankey-measure.js` because the module has none) is now the Sankey view in the app: the engine calls it when the page passes `sk` (`build(..., {view:'sankey', sk})`; without `sk` the old layered Sankey stays, which the lab page uses as "before"), the scene draws it (`sankeyBands`/`sankeyNode` in `src/scene.js`; gradients through `ribbon.color2`), and `src/app/33-sankey.js` holds the hand edits (`S.V.sk`: colors, labels, order, bar places; saved with the view and in shared view text via `cleanSk`), their undo, the Look panel section and the click menus. Items are keyed by data id (`nodeId`), never by the engine's `n0`, so remembered order and places survive rebuilds. Lab: `bench/sankey/` + `tools/build-sankey-lab.mjs` -> `bench/netflow-map-sankey.html` (before/after page), `test/sankey.test.js`, research in `docs/SANKEY.md`. Tester: `TESTER_ONLY=3d node bench/tester/run-local.js chromium` runs just the 3D step; `TESTER_ONLY=where` runs "Where the drawing time goes (WebGPU)" (`NFMProbe.frameTiming` / `explainTiming`: times each phase of a picture several ways, WebGPU against WebGL 2). Turning a big 3D map: `networkScene` keeps what each item and link looks like between pictures (`o.plan`), and `tessellate` in `src/render.js` writes plain straight links (every link on a big network) straight into one shared buffer, so a 3,000-item picture costs a few milliseconds there instead of fifteen; `test/force3d.test.js` checks both give the same picture. WebGPU keeps its buffers between pictures (`legacyBuffers` is the old make-new-ones way, for the diagnostic) and loops call `pace()` instead of waiting for the card after every picture; `test/probe.test.js` covers both with a pretend device. Card-side turning (3D network of 1,500+ plain straight links, no icons/arrows/bends): `makeRig`/`attachTurn` in `src/scene.js` give the scene `S.turnTo(cam,kmax)` which only works out camera numbers, the back-to-front order (radix sort) and the few visible names per angle; `drawRig` in `src/render.js` (WebGL 2 textures + WebGPU storage buffers, same fragment code as the normal drawing) does the projection, fading and link trimming on the card. `scheduleScene` in `src/app/30-map.js` uses it while turning (`S.turn.on`) and `settleTurn()` rebuilds the full identical scene 250 ms after the last angle (picking, exports, Canvas2D). Item records (`rec.x/y/w/h/o`) are refreshed lazily by `S.syncRecs()` (flag `S.recStale`; called by `pick`/`inRect`/`inLasso` and `sceneNodeFor`: anything new that reads item places after a turn must call it), the pick grid by `S.gridStale`; the name labels are kept and moved from angle to angle (`lpool`), so a turn allocates almost nothing. Tests: card-side block in `test/force3d.test.js`, card vs full picture in `test/browser.test.js`; the tester times it as "math on the card". Links are 4-point triangle strips whose texels carry both end places (`rig.edgeG`), so the card does no second look-up. WebGL 2 sends the paint order through a ring of 3 attribute buffers by default; `rigDebug.orderVia = 'texture'` (tester way `tex`) sends it through an RGBA32UI texture instead, same picture (checked in `test/browser.test.js`); keep the default until laptop results say which is faster. WebGPU has three ways too (`rigDebug.orderVia` / `out.orderVia`: `write` = one buffer + writeBuffer (default: on the laptop with no leaks it ran 60/60/56 at 100,000 items, p95 19 ms), `map` = five MAP_WRITE staging buffers written directly and copied on the card (45/53/55, worse) and `ring` = three buffers (46/38/37, worst); earlier runs that favored `map` were run while the destroy leak below was eating memory, so do not trust comparisons made on builds before v2026.10.16.2019); tester ways `ring`/`map` compare them to the default, and `explainSplit` blames the paint order when pauses vanish without the re-send (the "nothing drawn" row alone is not trusted: the refresh runs slower with an unchanged canvas). `NFMProbe.turnSplit` / `explainSplit` (tester section "Turning the largest map: where the time goes") splits that turning into angle math, card time (links, items, names, half size, via the renderer's `rigDebug` switches) and the spread of picture times, and says in words which one holds it below 60.
- WebGPU `destroy()` must destroy every buffer one by one (rings are arrays) and always call `device.destroy()` last; an early v2357 version threw on the ring array and skipped the device, leaking memory until 100,000-item tests ran out of memory (checked in `test/browser.test.js`: leaving WebGPU destroys the device).
- Tester page order: the step being tested is the top card while it runs (`addSection` inserts at the top); when it finishes `main.fin` puts the "All done" buttons first (CSS `order`), then the turning 3D map (`#show`), then every step back in test order.
- Tester live view: while a section runs, `s.rows.push` redraws its table at once (rows appear one by one), `setStatus` is mirrored into the open card's "Working… now testing" line, `s.scatter(X, k, caption, stride)` draws a flat picture of the positions just worked out, and `s.live()` makes a box that `NFMProbe.turning` / `turnSplit` / `frameTiming` draw into (option `live`; `mkHost` in probe.js scales the real 900x600 picture into it, otherwise the host stays almost invisible in the page corner). The box is removed when the section finishes.
- Tester sizes everywhere (not quick mode): 5,000 / 25,000 / 50,000 / 100,000 in the layout ladder (moderate to 100,000, complex to 25,000), the parallel-pairs variants (5,000 and 25,000, plus old steps at 50,000 and 100,000), the drawing-time step and the 3D section. The smooth sweep (`sgd`) is skipped above 30,000 items (minutes). The correctness check stays at 1,200 items because its reference runs on the processor. The extras-only steps are unchanged.
- Tester 3D section sizes are 5,000 / 25,000 / 50,000 / 100,000 (3D force is built up to 30,000, spheres and stacks above). The turning picture at the end (`addPreview`) uses the card path like the app (rig scene, `rigPrepare`, `turnTo` only when the angle changes or zoom passes kmax, one `resize`, draws only when something moved, eased wheel zoom) and has a button per size; it used to rebuild the whole scene and resize the canvas on every wheel tick, which made zooming out (every item on screen) awful. Rows named "zooming in and out on the card" come from `NFMProbe.turning({zoomSweep:true})` (a quarter size to four times). `?preview=webgl2` forces the preview backend for testing. The preview also has a live FPS pill and records frame gaps while the person drags, scrolls or lets it turn; the "Your hands-on test" table is added to the results every time Download or Copy is pressed.
- Zooming and panning a big 3D map (`requestDraw` in `30-map.js`) ride the card like turning does: the first moved view enters card mode (`turnTo`), there is no automatic rebuild after movement stops any more (`armSettle()` is a no-op): rebuilding the full scene froze the next drag (0.2 s at 25,000 items, 1 to 2 s at 100,000, plus a fresh upload to the card). Whatever needs the full scene calls `settleTurn()` (save, print) or reads through `liveScene()` (brings the lazy item records up to date); any content change rebuilds the scene anyway. `browser.test.js` checks zooming after a settle goes back onto the card. Note the test reads the scene state right after `settleTurn()` (before any awaited draw): a draw at a different view legitimately flips the settled scene back onto the card.
- Drawing backend order in the app is WebGL 2, then WebGPU, then basic drawing (`Manager.order` in `src/render.js`): on the laptop measured (v2319 results) WebGPU showed random 200-350 ms pauses even at 5,000 items while WebGL 2 held 60 FPS; Advanced still lets a person pick WebGPU. The tester's turning picture opens with WebGL 2 and has "Drawn with" buttons to swap backends by hand (hands-on rows are keyed per backend). `nextRefresh` in `src/probe.js` only reports "page in the background" when the page is really hidden or nothing came for 10 s. `rigWarm()` (both card renderers) puts a big 3D map on the card a moment after it appears (`warmCardSoon` in `src/app/30-map.js`), so the first drag does not pay for the upload and first-use shader work; the tester's "math on the card" note reports its time.
- Tester page top strip (sticky): progress bar, status line, an always-on FPS counter (`#fpsnow`, the page's own refresh rate) and a run clock (`startClock`/`stopClock` in `bench/tester/tester.js`); every live viewing box (`s.live()`) carries a real-time FPS pill (`addFpsPill`, a requestAnimationFrame counter with the slowest picture of the last half second).
- WebKit is in every test run: `node test/browser.test.js webkit` (WebKitGTK 2.52.6; `epiphany` for GNOME Web) goes through `bench/webkit-driver.js`, the same file as `tools/webkit-driver` in https://github.com/lfcfoundry/JS-modules (keep the two in step). Run Firefox, Chromium and WebKit one after another. A WebGL canvas that was shown is empty if read in a later task in WebKit, so the tests draw and read pixels in the same task. `WebGL2.destroy()` marks the renderer destroyed before it loses its context on purpose, so the late `webglcontextlost` event is ignored (the browser test switches WebGL 2 four times and checks for no false alarm).
