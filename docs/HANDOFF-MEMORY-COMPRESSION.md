# Handoff: memory compression for Netflow Map at 100,000 items

Copyright (c) 2026 LFC Foundry. MIT License. Written 2026-10-17 (US Eastern) for a fresh Claude context. You have no other background; everything you need to continue is here or in the files named here.

Owner: JNFoo ("JNFoo"). He is not a programmer. He wants plain words, real measurements, and the compute and time cost of every run (see "Standing rules" at the end).

## 1. The question this work answers

Netflow Map (`https://github.com/lfcfoundry/netflow-map`, one self-contained `index.html` built from `src/`) draws 3D networks of 100,000 items and about 300,000 links. On the owner's laptop (Firefox 159, Windows, integrated graphics) turning, zooming and dragging already hold 60 FPS at 100,000 items, because the picture is uploaded to the graphics card once (the "rig": `makeRig`, `attachTurn`, `S.turnTo`, `drawRig` in `src/scene.js` and `src/app/30-map.js`).

What hurts is MEMORY and the peak while building a new picture. The owner has another context building a general JS-object compressor (`memory-compression` and `memory-compression-jso` in `https://github.com/lfcfoundry/JS-modules`) and asked whether it can shrink what Netflow Map keeps in memory. This file is the result of testing it on the REAL layout and scene, not a synthetic list.

## 2. Short answer

- The memory is in JavaScript OBJECTS, not in numbers. The same data as typed arrays is a few megabytes.
- `memory-compression-jso` (the object packer) brings the real 100,000-item layout from about 151 MB of live objects down to **7 to 17 MB packed**, and gives back exactly the same objects (checked with `assert.deepStrictEqual`).
- The typed-array module (`memory-compression` 1.0.0 and 1.1.0) does not help on its own: the data is already small as arrays, and turning columns back into objects costs 1.6 s.
- **Recommendation (not yet built into the app):** hold the OLD layout packed (the `refs` option, 6.9 to 9.2 MB) while a new one is made, and rebuild the scene from the layout when needed. Do NOT pack the scene: the renderers read it continuously, and unpacking it takes 1.4 to 3.9 s.
- Two things are NOT settled and must be measured before anyone builds on this: single-item read speed (section 6) and the Firefox run (section 7).

## 3. What holds the memory (measured, Node 22.22.0, `--expose-gc`, 100,000 items, 299,762 links)

| Scene `S` (`S.curves`, `S.dots`, `S.labels`, ...) | 245 MB | sphere arrangement |

Building twelve pictures in a row makes about 1.4 GB of garbage; the collector frees it, but the peak is what a laptop feels.

## 4. Results: `memory-compression-jso` (object packer) on the real data

Module: `modules/memory-compression-jso` in `lfcfoundry/JS-modules`, **version 1.1.1** (merged to `main` as `9d6ae60`, 2026-10-17; the first measurements in this thread used 1.1.0 on branch `claude/project-thread-aa4864` and gave the same sizes and exactness). WebAssembly helper active (`accelerated() === true`). Command: `node --expose-gc bench/memory/jso-bench.js 100000`. The whole run takes about 70 seconds.

| Thing packed | Mode | Packed size | Pack | Unpack | Exact? |
|---|---|---:|---:|---:|---|
| Layout `L` | fast | 17.1 MB | 1,448 ms | 1,853 ms | yes |
| Layout `L` | fast + refs | **9.2 MB** | 993 ms | **436 ms** | yes |
| Layout `L` | small | 14.7 MB | 3,080 ms | 1,183 ms | yes |
| Layout `L` | small + refs | **6.9 MB** | 2,232 ms | 466 ms | yes |
| Scene `S` (data members) | fast | 38.2 MB | 1,936 ms | 1,410 ms | yes |
| Scene `S` | fast + refs | 49.4 MB | 5,574 ms | 3,899 ms | yes |
| Scene `S` | small | 34.6 MB | 2,336 ms | 1,766 ms | yes |
| Scene `S` | small + refs | 42.4 MB | 7,702 ms | 3,637 ms | yes |

How to read it:
- `refs` stores objects that are shared by reference once. It helps the layout a lot (nodes and edges point at each other) and HURTS the scene (bigger and slower). Use `refs` for the layout only.
- A second run (the first 1.1.0 run, before 1.1.1) gave the same sizes and timings within about 15%: the timings are noisy. Treat any single timing as plus or minus 30%.
- The scene was packed as a plain-data copy: `S` has no function members in this build (the benchmark prints `scene function members: 0`). If a later version of `src/scene.js` adds functions to `S`, the benchmark must copy only the data members as it does now.
- `view()` (lazy reading) opened a packed list of 299,762 links in 0.27 ms. See section 6 for what reading one link costs.

## 5. Results: `memory-compression` (typed-array module) 1.0.0 and 1.1.0

Module: `modules/memory-compression` (same repo). Command: `node --expose-gc bench/memory/mc-bench.js 100000` (about 28 seconds). I encoded each list of flat objects as a Float64Array of its numeric fields plus a text block for the string fields, then packed both.

| Part | Raw | fast | small |
|---|---:|---:|---:|
| Layout nodes (100,000 x 30 numbers, 9 text fields) | 28.5 MB | 8.3 MB (29%) | 7.5 MB (26%) |
| Layout links (299,762 x 5 numbers, 8 text fields) | 24.7 MB | 3.9 MB (16%) | 2.2 MB (9%) |
| Scene links (299,762 x 5 numbers, 5 text fields) | 83.6 MB | 42.4 MB (51%) | 28.8 MB (34%) |
| Scene dots (100,001 x 7 numbers, 2 text fields) | 14.0 MB | 3.6 MB (26%) | 2.9 MB (21%) |
| Scene labels (100,000 x 7 numbers, 3 text fields) | 12.9 MB | 3.1 MB (24%) | 2.9 MB (22%) |
| **Total** | **163.6 MB** | **61.4 MB** | **44.3 MB** |

Costs that decide it:
- Making the numeric parts of the 100,000 item objects and 299,762 link objects again from the columns takes **1,598 ms** (text fields extra). That is the cost of any "keep columns, hand out objects" design, whatever compressor sits under it.
- The whole layout as JSON text is 156 MB (1,767 ms to write, 1,505 ms to parse); packed by this module it is 39 MB (fast, restore 349 ms) or 24 MB (small, restore 382 ms). The object packer above beats that (9.2 MB or 6.9 MB, restore about 450 ms) because it packs by column and shares references.
- Conclusion: the typed-array module changes no speed that the page feels, and the memory it frees is only worth having if the objects are not rebuilt. It is the engine under the object packer, not the answer by itself.

## 6. Caveats you must carry forward

1. **Unpack time is not the 120 ms the module's own demo shows.** On the real layout, unpack was 0.44 to 1.9 s depending on mode and `refs`. The module's synthetic test used simpler objects. Do not promise the owner 120 ms.
2. **Reading one packed link was slow at 100,000 items.** `view(packed).get(i)` read 1,000 spread-out links in 224 to 226 ms (about 0.22 ms each); the same test at 3,000 items took 12 ms (about 12 microseconds each). It grew with size, which I did not explain. Picking and hover read single links, so ask the module's owner (or open `modules/memory-compression-jso/src` and profile `get`) whether the first access decodes whole columns lazily, and rerun with 10,000 reads after a warm-up read. Until that is answered, do not design anything that reads packed links inside a per-frame loop.
3. **The heap line in `jso-bench.js` prints "heap now 873 MB (was 873)".** That is not a failure of the packer: the benchmark still holds `dg` and other references to the layout, so nothing could be collected. The saving only exists if EVERY holder of the layout lets go. The holders in the page have not been listed or prototyped (candidates: the layout variable in `src/app/30-map.js`, `o.plan`, picking (`edgeIndex`), SVG and CSV export, the Canvas 2D fallback, `engine-client.js` results). That list is the first job of whoever builds this.
4. **Not measured:** the time to rebuild the scene from an unpacked layout (it is the existing `makeScene` cost, not timed in this study), peak memory while unpacking, and anything in Firefox, Chromium or WebKit. Node numbers are not the owner's laptop.
5. **Ruled out earlier (do not redo):** `releaseOldScene` (built, reverted: the renderers keep references to the old scene in `rigState.sid`, `sid2`, `sidT`, the WebGPU `rs.sid`, a stale `T`, and `S.keyMap.sc`; a throw while making the new one left `S.scene` null) and lazy link objects (`S.curves` is read by tessellation in `setScene`, `style()`, `rigStyle`, picking, SVG export and the Canvas 2D fallback). Full reasons are in `docs/MEMORY-AT-100K.md`.

## 7. What to do next (in order)

1. **Ask the owner first** (use AskUserQuestion; he asked to be asked at every chance): whether to proceed to a prototype now or wait for the next module version; whether the goal is lower steady memory, lower peak, or both.
2. Read the newest `modules/memory-compression-jso` (`README.md`, `CHANGELOG.md`, `src/`) on `lfcfoundry/JS-modules` `main`; the version may have moved past 1.1.1. Rerun `node --expose-gc bench/memory/jso-bench.js 100000` and put any change in this file.
3. Answer caveat 2 (single-read cost at 100,000) with a proper warm-up and 10,000 reads.
4. Run the benchmark inside Firefox 158, ungoogled-chromium 155 and WebKitGTK 2.52.6, ONE AT A TIME, with the version printed on line 1 (the browsers are on the `browsers` branch of `lfcfoundry/knowledge-base`; re-read its README first; the harness is `bench/webkit-driver.js` for WebKit, `test/browser.test.js` shows how the others are launched). The module has its own browser notes; its WebKit result drove the 1.1.1 change ("drop the text-column shortcut that slowed WebKit").
5. Make the holder list (caveat 3). Prototype only the layout: pack with `{mode:'fast', refs:true}` (or `small`) when a new layout replaces the old one, keep the packed copy, unpack on demand. Measure heap before and after in the page with the tester, not just Node.
6. Embedding rules for anything added to the page: one self-contained `index.html`, offline, the module's source and its WebAssembly bytes embedded with a plain-JavaScript fallback that gives the same answers, `'wasm-unsafe-eval'` in `script-src` only (owner's policy, 2026-10-17; the page has no policy today), MIT-compatible code only, source of the module recorded with its version and commit. Netflow Map already embeds one WebAssembly helper (`wasm/`, see the repo-move handoff) as an example of the pattern: `wasm/build.sh`, `wasm/embed.py`, bytes between `WASM:BEGIN` and `WASM:END` in `src/engine.js`, and a test that checks identical answers.
7. Tests to add with it: pack and unpack an `E.build` layout and `assert.deepStrictEqual` it (the benchmark already does); the page must draw the same pixels with and without the packed path (`test/browser.test.js` parity check); one case where the module is missing or fails and the page keeps working.
