# Changelog

Copyright (c) 2026 LFC Foundry. MIT License.

What changed in Netflow Map, in plain words, newest first. Each build is stamped `year.month.day.HHMM` (US Eastern) in the page header. This is the short list for people who use the app. The long version for each build (every measurement, test count and tool change) is kept in the private knowledge base, under `projects/netflow-map/changelogs/`.

Tested one browser at a time in Firefox 158.0, ungoogled-chromium 155.0.8059.39, WebKitGTK 2.52.6 and GNOME Web 46.5. Not tested for any build: Safari itself, any iPhone, Chrome on a phone.

## October 25

- **2026.10.25.2230** Big maps use less memory: the lists of links going in and out of each item are now two number lists instead of one list of objects per item (30,000 items, 94,597 links: whole page memory 18.4 to 12.5 MB in Chromium). Showing which items touch the selected ones is slightly slower for a single item (about 2 microseconds more) and faster for thousands of items in WebKitGTK. New test: the same links in the same order as before.
- **2026.10.25.2125** Fixed two video file bugs: some browsers (Firefox) refused the MP4 because three header flags were written in the wrong place, and the seek points in longer WebM videos were a few bytes off. New test for both.
- **2026.10.25.2110** Fixed the map going black after a change on a big 3D map (for example Look, Arrangement, Distances 3D (stress) on 30,000 items): the graphics card's pre-load drew into the picture the browser was showing and left it empty until you pressed Fit. The pre-load now draws into a picture of its own.
- **2026.10.25.1326** The GIF maker can now save a video instead: new "File type" choice (GIF, or Video, which is MP4 where your browser can make it and WebM otherwise; if it can make neither you get a GIF and are told). On a busy 30,000-item map a video came out at about 0.6 MB per 100 pictures against about 5 MB for the GIF (lower is better). A new line under the choices says how many pictures and about how big the file will be before you start. The legend has a new "Legend" choice: Short (the default: the first six groups, then "+ N more", with the size, line width and marker lines in a smaller block), Full (every group) or Off, and the old "Include the key" box is gone (an old Off setting carries over). The video plays in the page (it shows its first picture until you press play), and you can save it. The page's security rules gained one line for this, `media-src blob:`: only files made in the page itself.
- **2026.10.25.1245** The key (legend) on big maps is tidier: when it has many rows it uses up to three columns and ends with a "+ N more" line instead of one very tall column. New "Where the key goes" choice for GIFs (bottom left, bottom right, top left, top right). Keys with few rows look the same as before.
- **2026.10.25.1237** New "File size" choice for GIFs (Best picture, Smaller file, Smallest file; Smaller is the new default). On a busy 30,000-item map the file went from 6.9 MB to about 5.3 MB (lower is better) with Smaller and about 4 MB with Smallest. Turning the other way after each pause now also turns the other way at the pause where the GIF starts over (an odd number of turns is rounded up to even).
- **2026.10.25.1218** The GIF maker draws its pictures on a canvas kept in memory instead of one held on the graphics card. On one laptop drawing a picture took 21 ms instead of 103 ms (lower is better), so GIFs finish much sooner. The map on screen is not changed.
- **2026.10.25.1212** Making a GIF waits less between pictures, so a GIF without a look finishes about 10 to 20 percent sooner (Chromium 19.4 to 17.4 ms a picture, Firefox 18.3 to 14.8; lower is better). Pictures are identical.
- **2026.10.25.1200** The GIF looks (glow, blur, sharpen, colors) are now done by your graphics card when there is one, with the processor as the backup, so a GIF with a look finishes much faster (on one laptop the looks took 13 ms a picture instead of 38 ms; lower is better). There is a new "Graphics card" choice in the Look section, set to automatic. The card does the same arithmetic as the processor, so a picture may differ by a color shade or two between computers.
- **2026.10.25.1124** GIF picture looks (glow, blur, sharpen, color) now run in WebAssembly, so a GIF with a look finishes about twice as fast on one worker (WebKitGTK 9.7 to 3.9 s, Firefox 5.7 to 2.9 s, Chromium 5.4 to 3.2 s; lower is better). Pictures are byte for byte the same as before; where WebAssembly is missing, the old code runs.
- **2026.10.25.1051** The GIF maker is much more flexible: a very smooth 25 FPS (every picture shown for exactly 0.04 seconds), turns that can pause between each other and turn the other way after each pause, a short swing instead of a full turn, six kinds of easing, names that show always, never, only when the map holds still, or when it slows down, and a look for the whole animation (brightness, contrast, color strength, warm or cool, tones such as old photo or black and white, soften, sharpen, glow, darker corners, nine ready-made looks) with a button to try it on one picture first. The work now runs in background workers, so the page stays free.
- **2026.10.25.1018** New Colors tab on the Map: pick a ready-made look (12, including Blueprint, Paper, Colorblind-safe, High contrast and Print gray) or change the color of every part yourself (background, boxes, text, links, highlights, good and bad, bands, twelve group colors, the number scale), the type family, and the size of items, names and lines. Looks are saved with the map, kept in My looks in this browser, and can be saved to a file and opened on another computer. The animated GIF follows your colors. Maps with no look chosen are drawn exactly as before (30,000-item rebuild 248 to 241 ms in WebKitGTK, lower is better).

## October 24

- **2026.10.24.2045** Big maps with link rules, dashes, arrowheads or bent links are now kept in the compact flat lists too, so they rebuild faster after moving items (30,000 items, rebuild 143 to 128 ms in Chromium, 158 to 137 in Firefox, 228 to 212 in WebKitGTK; lower is better). Pictures are identical.
- **2026.10.24.1903** No change you will notice: the picture-building code now comes from the shared netflow-scene module (JS-modules) instead of a private copy, so Netflow Map and other projects stay in step. Same pictures; rebuilding a 30,000-item picture is the same speed (Chromium 103 to 101 ms, Firefox 114 to 107, WebKitGTK 164 to 159; lower is better).
- **2026.10.24.1412** Moving items and changing label sizes on a big flat map rebuild the picture 1.2 to 1.4 times as fast again, with a shorter freeze: links are built straight into flat number lists instead of one object each (30,000 items, rebuild 113 to 91 ms in Chromium, 330 to 234 in Firefox, 192 to 161 in WebKitGTK; longest freeze 152 to 120, 387 to 306, 416 to 342; lower is better). Pictures are identical. Maps with link rules, arrows, 3D or fewer than 2,000 links build as before.
- **2026.10.24.1331** A second copy of Netflow Map opened in the same browser (another tab, or an old and a new build) no longer overwrites the saved map of the first. The second copy shows "Open in another tab", saves nothing, and offers "Use this tab" to take over (the other copy then gets the card). Start-up is unchanged (Chromium 96 to 95 ms, Firefox 135 to 137, WebKitGTK 89 to 89, median of 11 fresh pages). Uses tab-guard 1.1.0 from JS-modules, which needs the Web Locks API; without it nothing changes.
- **2026.10.24.1303** Moving an item and changing label sizes rebuild the picture of a flat map 1.1 to 1.2 times as fast: each link's look (width, color, dash, arrow) is kept from the last picture instead of worked out again (30,000 items, rebuild 111 to 90 ms in Chromium, 127 to 105 in Firefox, 146 to 132 in WebKitGTK; lower is better; the longest freeze ties). Any other change to the look (line width, curves, rules, key edits, theme, states) still starts over, and pictures are identical.
- **2026.10.24.0913** Flow, Down, Spine and Lanes layouts are 1.0 to 1.9 times as fast (netflow-layers 1.5.0: the row-order search and row placement now run in WebAssembly, with plain JavaScript as the fallback; the page rule already allowed it). A 5,000-page map lays out in 510 to 297 ms in Chromium, 567 to 328 ms in Firefox and 390 to 275 ms in WebKitGTK (lower is better; first layout of a fresh page); a 300-page map gains little (13 to 8, 20 to 18, 10 to 10 ms). The pictures are exactly the same (576 layouts compared, 0 different).
- **2026.10.23.2351** Parking the links of a big map is faster with memory-compression 2.6.2 (was 2.4.9): packing 100,000 items takes 200-210 to 147-152 ms in Chromium, 286-306 to 257-275 in Firefox and 203-214 to 178-193 in WebKitGTK (lower is better); waking the links ties (30,000 items over 40 rounds: Chromium 32-34 ms before and 32-33 after, Firefox 36-38 and 35). The page is 17.7 KB larger. Nothing drawn changes.
- **2026.10.23.2338** A packed link list could be left unreadable if it was parked by hand while the idle background pack was part way through (the next link read failed with "reading 'edges:0'"): the background pack now gives way when anything else took over. Found by a 100,000-item timing run; the 2,000-item run never starts that pack. New test fails before and passes after; all 33 Node tests and the browser test pass in Chromium (186 checks), Firefox (174) and WebKitGTK (174). Nothing drawn changes.
- **2026.10.23.2131** Basic (Canvas 2D) drawing is faster for straight links: they are drawn as lines instead of curves that happen to be straight. At 93,232 links one draw takes 757 to 629 ms in Chromium, 462 to 385 ms in Firefox and 7,258 to 934 ms in WebKitGTK (lower is better). Edge pixels differ slightly: 99.84% or more of color values within 5 of 255 in all three. Big maps on the graphics card are not affected.

## October 23

- **2026.10.23.1716** A big map left alone for a few seconds comes back without holding the page: waking the parked links at 100,000 items holds the page 222 to 34 ms in Chromium, 273 to 14 ms in Firefox, 207 to 19 ms in WebKitGTK and 190 to 23 ms in GNOME Web (lower is better); it also uses memory-compression 2.4.9 (waking all at once alone is 125 / 101 / 101 / 125 ms). The page is 30 KB larger. Nothing drawn changes.

- **2026.10.23.1631** Less memory churn when the picture of a big map is rebuilt with basic (Canvas 2D) drawing: at 100,000 items a rebuild makes 64 MB of short-lived data instead of 171 MB, and the page holds 305 MB once idle instead of 408 MB (lower is better); the picture is identical byte for byte. Drawing with the graphics card (WebGL 2) changes by about 4 MB only.

- **2026.10.23.1021** The Force arrangement of a map with 20,000 or more items can now be done on the graphics card, but only on a device where a quick timing says it is faster. At 100,000 items the whole layout took 26.2 s on the processor and 5.6 s on the card on a laptop with integrated graphics (4.7 times faster, 200,000 items 2.0 times; lower time is better), and the layout is as true (truth score 0.210 for both; lower is truer). A midrange phone (Android, Chrome) was slower on the card at 100,000 items (42.4 s against 24.2 s), so there it keeps using the processor; its timing check costs about two card rounds. Check this device now lists what to expect on each kind of device.

- **2026.10.23.0802** Plain straight links can now go to the graphics card as 9 numbers each instead of 60, the card building each link's quad itself (WebGL 2 only; arrows, curves, dashes and ribbons keep the old way). Putting 100,000 straight links on the card takes 3.0 to 4.0 times less processor time (lower is better): Chromium 23.8 to 7.9 ms, Firefox 26 to 8, WebKitGTK 12 to 3, GNOME Web 11 to 3; the data sent shrinks from 22.9 MB to 3.4 MB, and the pictures are exactly the same (0 of 255 mean difference). The app measures once, on your own card, whether this is faster to draw and keeps the old way when it is not: on the test machine's software drawing it kept the old way in all four browsers, so nothing changes there. Real-card speeds come from the Netflow Map Tester's new "Straight links on the card" step. Tests: 185 / 173 / 173 / 173.

- **2026.10.23.0007** Flow, Down, Spine and Lanes layouts are 4 to 24% faster again (netflow-layers 1.4.0; the pictures are exactly the same in 576 of 576 comparisons). First layout of a 3,000-page map (lower is better): Chromium 237 to 216 ms, Firefox 272 to 244, WebKitGTK 218 to 188, GNOME Web 213 to 194. Fixed: clicking an item on the old picture while new data was still being laid out could show "cannot read properties of undefined" in the details panel. A new random-use test (12,000 random pans, zooms, setting changes, item moves and file loads in the four browsers) found it and now finds nothing.

## October 22

- **2026.10.22.2121** Panning and zooming a big map with the basic (Canvas 2D) drawing is much smoother. While the camera moves, the last picture is slid and scaled instead of drawn again, and the sharp picture is drawn again a moment after you stop; at rest it is exactly the same as before. On a 1,500-item Sankey map, panning goes from 14 to 60 frames a second in Chromium, 23 to 60 in Firefox, and 2 to 28 and 2 to 22 in the two WebKit browsers; Flow and Network maps gain as much. Also new: hidden Save speed report and Save error log buttons (five quick taps in the top-left corner open them; nothing is sent anywhere), and the memory-compression piece is now version 2.3.4. The page opens in the same time as before.
- **2026.10.22.1947** Big Flow, Down, Spine and Lanes maps now draw. Before, a map of about 5,000 pages or more (with chapter folding off) was refused as "too big"; now maps up to about 250,000 stops (about 6,500 pages with 3 links each) draw, in 0.5 to 1.6 seconds for 5,000 to 6,500 pages. Smaller maps take the same time. Bigger ones are still refused, with the same plain message.
- **2026.10.22.1845** Flow, Down, Spine and Lanes layouts of a few thousand pages are built faster, and the pictures are exactly the same. The layered drawing is now netflow-layers 1.3.1. First layout of a 3,000-page map (lower is better): Chromium 447 to 248 ms (1.8 times faster, higher is better), Firefox 551 to 294 ms (1.9 times), WebKitGTK 469 to 211 ms (2.2 times), GNOME Web 454 to 215 ms (2.1 times); a 1,000-page map is 1.5 to 1.7 times faster, and a plain 20,000-page tree 1.1 to 1.2 times. The page file grows 0.19% (999,600 to 1,001,498 bytes).
- **2026.10.22.1253** Letting go of an item you moved on a big Network map no longer freezes the page. Before, the drop built the whole picture again; now it only refreshes the outer box, the click grid and the link hover, and the picture is identical. Main-thread time of the drop on a 10,000-item map with 31,026 links (lower is better): Chromium 106.8 to 2.3 ms (46 times faster, higher is better), Firefox 203 to 3 ms (68 times), WebKitGTK 84 to 19 ms (4.4 times), GNOME Web 84 to 20 ms (4.2 times). The page file grows 0.08% (998,834 to 999,600 bytes).
- **2026.10.22.1227** The first grab of an item on a big Network map no longer stalls. Before, picking up an item on a map with tens of thousands of links first unpacked the whole stored link list; now the app moves the links in place and the list stays packed. Main-thread time for the first move on a 10,000-item map with 31,026 links (lower is better): Chromium 18.9 to 8.4 ms (2.2 times faster, higher is better), Firefox 20.0 to 6.0 ms (3.3 times), WebKitGTK 30 to 23 ms (1.3 times), GNOME Web 28 to 24 ms (1.2 times). Later moves are unchanged and pictures are identical. The page file grows 0.1% (997,825 to 998,834 bytes).
